# Audit: `career_clean/` — value extraction & output usability

*Full-scale read-only audit, 2026-06-10. All numbers measured against the real data.*

**Scope measured:** `parsed/experience` (9,076,606 rows), `parsed/positions` (2,788,549 rows), `normalized/career_steps.parquet` (10,800,787 rows, 2.78 GB), `paths/steps.parquet` (10,798,352), `paths/transitions.parquet` (6,018,391), plus all downstream consumers.

**Overall verdict:** the module is in excellent shape on its declared targets — company (F1 1.0, 72.5% of rows on a stable `company_id`), title (98.5% parsed to `level|base`), employment_type (100% rows classified), occupation (precision-1.0 SOC backbone). The raw parser drops nothing (a 20k-profile sample of the raw JSONL shows every experience/position key is captured; the one unparsed field, `positions.meta`, is verifiably redundant with `start/end_date`, which are 99.92% populated on positions). The gaps are (a) built-and-measured signal that never landed in the production table, (b) one cross-module seniority lexicon mismatch, and (c) output-format/bloat issues.

## Prioritized findings

### 1. Occupation coverage cliff: 21.5% SOC coding → only 7.84% of transition edges usable on the flagship axis — and the two proven extensions are not in production. (Effort: M)
- **Today:** `occupation_code` is non-null on 21.46% of career_steps (`onet_exact` 16.98%, deleveled/token ~4.3%; 75.82% `unmatched`, 2.7% deliberately blocked). Downstream, `transition_network/occupation_manifest.json` shows the occupation network — the v1 default axis per `CAREER_TRANSITION_NETWORK_PLAN` — covers **471,815 of 6,018,391 transitions (7.84%)**, a small and occupationally-biased subset.
- **Left on the table:** two extensions career_clean itself built and measured: (i) the anchored-embedding SOC proposer (`approach_c_embed.run_anchored_occupation`, measured 92% coverage in `results/occupation.json`) exists only as a benchmark — no proposals parquet / review-queue artifact exists anywhere in the repo; (ii) description-based occupation inference (`se_description.py`, measured +10.4pp cluster coverage with precision-graded confidence on SE rows) is applied only to the 459K self-employment rows — yet **51.8% of all 8.48M occupation-uncoded rows (4.39M rows) carry a description**.
- **Recommendation:** materialize `normalized/mappings/career_occupation_proposals.parquet` (title → SOC candidate, cosine, confidence, propose-only) from the existing anchored runner, and generalize the `se_description` lead/vote miner to the full uncoded population as a second propose-only column. Both stay out of the deterministic backbone, consistent with house style, but give the occupation network and industry's `occupation_prior` an immediate, confidence-thresholded coverage lever.

### 2. Seniority lexicon misses `manager`/`supervisor`: 1.67M steps have observable seniority that downstream cannot see — and `paths` has a dead rank entry waiting for it. (Effort: S)
- **Today:** only 29.12% of career_steps carry a *named* seniority token, so 84.17% of transitions get `seniority_direction='unknown'` and only 15.83% have lexical seniority on both endpoints. `career_clean/approach_a_rules._LEVEL_TOKENS` omits `manager` and `supervisor` — but `paths/common.SENIORITY_RANK` contains `"manager": 6`, **a token career_clean never emits** (verified: the token never appears in `seniority_level`). The consumer plainly expected it.
- **Measured:** 1,806,699 steps (16.7%) have "manager" in the raw title; **1,511,015 of them have no named level token** (→ NULL ordinal downstream); "supervisor" adds 160,559 more. Fixing this raises named-token step coverage from 29.1% to ~44.6% and roughly doubles both-endpoint edge coverage.
- **Recommendation:** don't move `manager` into the level-signature (that would change `role_canonical` identity, e.g. "Account Manager" → base "account"); instead emit a *separate* `seniority_rank_token`/ordinal column from career_clean computed over an extended lexicon (manager, supervisor, also `gm`, `md` candidates), leaving the literal canonical untouched. Also note 19,146 steps carry noise tokens `lvl6`–`lvl19` from 2-digit numbers in titles ("Region 12") — clamp the numeric-band rule to ≤5 or known patterns.

### 3. Self-employment functional clustering: built, tested, evaluated (11.9% → 40.6% → 50.5% coverage) — and absent from `career_steps.parquet`. (Effort: S–M)
- **Today:** four modules (`se_qualifier`, `se_personal_brand`, `se_cluster`, `se_description`) + production entry point `final_hybrid.canon_functional_cluster_value` + tests + evals (`results/self_employed_eval.json`: coverage on the 459,120-row SE population lifted from 11.9% SOC-only to 40.6% with title/company recs; `results/se_description_eval.json`: 50.5% with descriptions). **No `functional_cluster` column exists in career_steps**; the only non-career_clean consumers are an exploration script and the regression checker. `build_normalized.py` never calls it.
- **Recommendation:** add `functional_cluster` / `functional_cluster_method` / `confidence` columns (or a mapping parquet) in `build_normalized`. This directly serves industry's row-grain `nonorg:` handling (industry/common.py explicitly defers nonorg rows to "the occupation/description signal") and the spine's self-employment transition kinds.

### 4. Output bloat: ~43% of the 2.78 GB career_steps file is columns no downstream consumer reads. (Effort: S)
- **Measured column sizes:** `description_html` 875 MB (31.4%), `company_logo_url` 245 MB (8.8%), `url` 61 MB (2.2%), `subtitle` 12 MB, `subtitle_url` ~0 (0.01% populated — the PLAN itself says "100% NULL — drop"). Grep across paths/, industry/, transition_network/, cohorts/ shows **zero** references to any of these. `description` (855 MB) *is* used (industry LLM sampling, SE miner) and should stay.
- Also: `normalize_description()` exists in `final_hybrid` (FINDINGS: changes 35.3% of values) but **is never applied** — career_steps carries the raw description.
- **Recommendation:** drop `description_html`, `company_logo_url`, `subtitle_url`, `url`, `subtitle` from career_steps (all remain available in `parsed/` for re-joins by key) and store the NFKC-normalized description. Halves the file and removes the dead Phase-0 promise.

### 5. `role_canonical` is a compacted sorted-token string — unreadable node labels propagate all the way to the network outputs. (Effort: S)
- **Today:** `canon_title` compacts the sorted base (`base.replace(' ','')`), so `role_canonical` values are `managerproject`, `engineersoftware`. Verified in `transition_network/role_nodes.parquet`: top node labels are literally `managerproject`, `engineersoftware`, `president`, `account` — the role axis has no human-readable label (occupation gets one via the O*NET join; role doesn't).
- **Recommendation:** emit a `role_display` per canonical (modal raw title, or the pre-compaction spaced base) in the title mapping and carry it into career_steps. The information exists inside `parse_title` and is discarded one line later.

### 6. Location: 63.8% populated, 555,398 distinct raw strings, zero normalization. (Effort: M–L)
- **Today:** `location` passes through raw; `transitions.parquet` carries `from_location`/`to_location` but no consumer can use them (the same place appears as "New York, NY", "New York, New York, United States", "Greater New York City Area", …). ~72% of values look mechanically parseable (US state/`, United States`/`Area` patterns). `CAREER_PATHS_PLAN` §5b already calls for a place canonicalizer ("present but very messy — its own ER problem"); it was never built, making geography the only PLAN-named axis with no cleaner at all.
- **Recommendation:** a deterministic gazetteer pass (country → US state → metro) in the curation-ratchet style would likely resolve the head quickly given the heavy concentration (top-10 strings already cover ~7% of populated rows). Enables the relocation dimension downstream.

### 7. Smaller items (each S)
- **Duplicate stints survive:** 34,144 surplus rows (0.32%) share identical (person, company, title, start, end). PLAN measured this (0.35%) but no dedupe/flag exists; these create spurious self-loop transitions. Add an `is_duplicate` flag or drop-keep-first in `build_normalized`.
- **Curation ratchet barely seeded:** `ENTITY_ALIASES` has 3 entries (facebook/metafacebook→meta, alphabet-inc→google); the "review queue" appears in 10 docstrings but has no artifact or tooling. The 26.0% no-id company tail (`raw` 25.06% + `typo` 0.93%) has no path to shrink in practice.
- **Employment-type mapping is the build's long pole (558.7s of 925.3s)** because it's keyed on 9.34M distinct (company,title) pairs — near row grain. The resolution is a pure function of already-mapped value-level signals; computing it inline in SQL (title-status → company-placeholder → solo/owner markers) would cut build time ~2× and remove the largest mapping file.
- **Gold sets remain thin** (23 company / 18 title / 8 occupation pairs), acknowledged in FINDINGS; the occupation-proposer P=1.0 on 8 pairs is untrustworthy by the module's own admission — worth expanding before finding #1 ships proposals.
- **Date strings pass through by design** (paths parses them well, with granularity flags) — no change needed, but note `industry/` consumes career_steps directly and cannot tenure-weight company aggregates without re-deriving dates; if that ever matters, move `start_dt/end_dt/tenure_months` upstream into career_steps.
- **No url-slug backfill opportunity exists** (0 rows have a `linkedin.com/company/` url but NULL `company_id`) — the PLAN's "redundant" call is verified correct; no action.

## TL;DR — top 3 highest-leverage improvements
1. **Ship the already-built occupation extensions** (anchored SOC proposals parquet + generalize the description miner beyond SE rows): the 21.5% SOC rate collapses to 7.84% edge coverage on the default network axis, while 4.39M uncoded rows have descriptions and a 92%-coverage proposer sits unused. (M)
2. **Add `manager`/`supervisor` to a seniority-rank output** (separate from the literal canonical): fixes a verified dead `SENIORITY_RANK["manager"]` entry in paths and lifts named-seniority step coverage 29.1% → ~44.6%, roughly doubling directional transition coverage. (S)
3. **Land the SE functional cluster and slim the table**: write the evaluated `functional_cluster` column into career_steps, drop the 1.19 GB (43%) of never-read columns (`description_html`, logos, urls, subtitles), and apply the existing-but-unused `normalize_description`. (S)
