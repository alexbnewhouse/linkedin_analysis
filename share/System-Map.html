System Map

How the numbers travel from raw career histories to the page — what is built today, and what we build next so the portal updates itself when new data arrives.

Built works today (research prototype) To build designed, needed for production

The flow, end to end

Four shared stages turn raw profiles into vetted aggregate numbers. After that the flow forks: the left lane is how the prototype ships today; the right lane is the production target that removes manual rebuilds.

1

Data sources

Built · snapshot ingest

LinkedIn profile snapshots — roughly 2 million career histories. New snapshots arrive periodically.

2

Normalization spine

Built

Cleans and parses raw profiles into three canonical tables: education records, career steps, and job-to-job transitions.

3

Coding layer

Built · research-grade

Three coders turn free text ("Sr. Comms Manager") into analyzable categories. Every label carries a tag saying which coder produced it.

Lexicon coders Deterministic rule lists. When they match, they always win.
Occupation jury Calibrated LLM panel that sorts job titles into occupation groups.
Field-of-study jury Calibrated LLM panel that sorts degree text into fields of study.

Each jury must pass a pre-committed accuracy gate plus a bias check before any of its labels are used.

4

Aggregation pipeline

Built · batch scripts

Computes every number the portal shows — cohort funnels, destination fans, long-view curves, sectors, success pillars, counted pathway routes — under fixed rules: equal observation windows for every graduate, minimum cell size n ≥ 40 (smaller cells are suppressed), and aggregates only, never individuals.

The same aggregates can be delivered two ways — this fork is the whole difference between prototype and production.

Today · research prototype

Rebuilt by hand-run scripts after each pipeline run.

JSON contract

Built

One file, portal_data.json, holds every published number. Its shape is the data contract — the database on the right is this file, turned into tables.

8

Static export

Built

A build script injects the JSON verbatim into an HTML template, producing one self-contained page — shared as a zip and a hosted artifact. Opens in any browser, no server needed. This export stays in production as an offline artifact generated from any release.

Target · production

Same pipelines, feeding a live store — no manual rebuilds.

5

Live aggregate database

To build

Stores only aggregates — never individual profiles. Each pipeline run writes a new versioned release with its date and gate results; the portal always reads the latest published release; old releases are kept for audit. (e.g. Postgres — table sketch below.)

6

Read API

To build

Thin, read-only layer — REST endpoints, or simply static JSON files per release. Suppression is enforced upstream: a cell under n = 40 never enters the database, so the API cannot expose one.

7

Portal web app

Prototype built Production app to build

The three-layer product the team knows: Stories (guided walks; editorial routes badged amber), Portal (the live explorer), and Data & Methods (auto-generated from the release's gate results and provenance).

Why this matters for design: in production, nothing on the page is typed in by a person. The portal displays whatever the latest release contains — so every number the UI shows needs a home in the release schema, and every editorial addition needs its amber badge.

The update cycle

What happens when a new data snapshot arrives. If a quality gate fails, the release is held and the portal keeps showing the last good one.

New snapshotFresh profiles land.
Pipelines re-runSpine, coding, aggregation.
Juries recalibrateLLM coders re-checked on gold labels.
Gates + bias checksPass, or the release is held.
Release publishedNew versioned row-set in the database.
Portal reflects itAutomatically — no rebuild, no re-typing.
"Numbers can never drift from the pipeline — the portal displays a release, never hand-entered data." The one-sentence contract between data team and design team.

Front-end guidance

Consolidated from the team's UI/UX draft and the shipped prototype — one voice, with the project's identity and data rules applied.

  • Keep the interaction ideas Stateful URLs (every filter change updates the URL, so sharing a link shares the exact view) · one-click export of a view to PNG/PDF for slide decks · skeleton loaders shaped like the layout, never spinners · smooth animated transitions when a selection changes · clear hover states and fast tooltips showing the exact share, count, and source badge.
  • Pathway flows are now real — draw them Counted occupation-group routes (n ≥ 40) support Sankey-style flow rendering: hovering a group highlights its incoming/outgoing routes. Only published routes exist in a release, so the UI can never draw an unsupported flow.
  • Filters select among precomputed aggregates Major, population boundary, horizon, compare-with-baseline. A filter never queries raw rows — it chooses which released, already-suppressed aggregate to display. A brand-new cut (say, a new horizon) is a pipeline change that ships in the next release, not a UI feature.
  • The identity is already decided — and validated Violet accent (#4a3aa7 light / #9085e9 dark), Iowan Old Style/Palatino serif display, system sans body, both themes, emphasis-form charts (violet subject, gray baseline), earnest evidence-forward copy. Not Inter-plus-teal, no glassmorphism — the portal should feel like a research institution, not a SaaS dashboard.
  • What we deliberately do not build No demographic filters or breakdowns (the pipeline holds no demographic data, and the project makes no representativeness claims) · no row-level or free-form querying (aggregate-only) · no unbadged figures (every number carries pipeline-green or editorial-amber).

Design principles carried into production

  • Aggregate-only, always No individual profile ever reaches the database, the API, or the page.
  • Suppression happens upstream Cells under n = 40 never enter the database, so no UI state can leak one.
  • Provenance is a first-class UI element Pipeline data (green) vs editorial (amber) badges on every figure — designers own this distinction.
  • Gates hold releases, humans sign off A failed accuracy or bias check blocks publication; a person approves every release the portal shows.
